# API для мобильного приложения Gladiators

Предлагаемый контракт для первой интеграции. Сейчас приложение работает на моках в `src/api/`.

## Общие правила

- Сервер: `https://api.gladiatory.ariesdev.kz`. Полный базовый URL: `https://api.gladiatory.ariesdev.kz/api/mobile/v1`.
- Все ручки приложения находятся под отдельным префиксом `/api/mobile/v1`, чтобы не смешиваться с остальными API проекта.
- Пути ниже указаны относительно этого префикса: например, `/auth/code` — это `/api/mobile/v1/auth/code`, а `/me/membership` — `/api/mobile/v1/me/membership`.
- Запросы и ответы — JSON по HTTPS.
- Ключи JSON и query-параметров — в `snake_case`. Мобильный HTTP-клиент автоматически преобразует их в `camelCase` для экранов и кеша; строковые значения не меняются.
- Получение кода, проверка кода и чтение `/club` доступны без токена. Остальные запросы требуют `Authorization: Bearer <token>`. Пользователь определяется по токену, передавать его ID не нужно.
- ID и номера шкафчиков — строки. Даты и время — ISO 8601 с часовым поясом, например `2026-11-23T23:59:59+05:00`.
- Часовой пояс проекта фиксирован на UTC+5 (`Etc/GMT-5` в PHP, `+05:00` в соединении MySQL). Для старых посещений сохраняется момент события: MySQL сам преобразует `TIMESTAMP` при чтении; вручную сдвигать историю не нужно. Календарные сроки абонементов не сдвигаются.
- Обязательные текстовые поля приходят заполненными. `null` используется только в явно указанных местах; пустые списки возвращаются как `[]`.
- Отсутствие абонемента, ключа или посещений — успешный ответ, а не ошибка сервера.

## 0. Настройки приложения до входа

**`GET /config`** — публичная ручка `/api/mobile/v1/config`, без токена. Приложение вызывает её при каждом запуске, до авторизации. Ответ не зависит от клиента и клуба. Последний успешный ответ сохраняется на устройстве; при сетевой ошибке приложение использует сохранённую копию, а при её отсутствии показывает ошибку с кнопкой «Повторить».

```json
{
  "data": {
    "contacts": [
      { "title": "Позвонить", "url": "tel:+77758761111" },
      { "title": "Написать в WhatsApp", "url": "https://wa.me/77758761111" }
    ],
    "app": {
      "min_version": "1.0.0",
      "store_url": { "ios": "#", "android": "#" }
    },
    "maintenance": { "enabled": false, "message": null },
    "links": { "privacy_policy": "#" },
    "realtime": {
      "key": "public-reverb-key",
      "host": "api.gladiatory.ariesdev.kz",
      "port": 443,
      "scheme": "https"
    }
  }
}
```

- `contacts` — общий список способов связи до входа, минимум одна строка. `title` и `url` открываются приложением как есть; порядок сохраняется. Допустимы `tel:` и ссылки на мессенджеры и соцсети; предпочтительны HTTPS-ссылки (`wa.me`, `t.me`). Эти контакты настраиваются отдельно от профиля конкретного клуба в `/club`.
- `app.min_version` — минимальная версия `X.Y.Z`; более старые версии приложения должны показывать обязательное обновление с переходом по `store_url.ios` или `store_url.android`.
- `maintenance.enabled` — мобильный режим технических работ. При `true` приложение показывает `message` вместо интерфейса; при `false` сервер всегда возвращает `message: null`. Этот флаг не выключает сам API и не мешает загрузке `/config`.
- `links.privacy_policy` — ссылка на политику конфиденциальности. Пока ссылки магазинов и политики не заданы, возвращается `#` по согласованному правилу. Приложение не должно открывать `#` как рабочую ссылку; перед включением обязательного обновления нужно заполнить ссылки магазинов.
- `realtime` — публичные параметры подключения к Reverb. `key` берётся из `REVERB_APP_KEY`; секрет и ID Reverb-приложения не передаются. `host`, `port`, `scheme` берутся из публичного `APP_URL`: Reverb уже проксируется nginx на том же домене. `host` содержит только имя хоста, `port` — явно заданный порт или стандартный 443/80, `scheme` — `https` или `http`. Внутренние `REVERB_HOST=reverb`, `REVERB_PORT=8080` и `REVERB_SCHEME=http` из Docker в ответ не попадают.

Настройки хранятся в БД в таблице `mobile_app_settings`, запись `id=1`. JSON-поля `contacts`, `app`, `maintenance`, `links` соответствуют одноимённым блокам ответа. Изменение записи применяется при следующем запросе, без перезапуска приложения и обновления кеша конфигурации. Дополнительных переменных `MOBILE_*` нет. Настройки являются общими для приложения; до входа определить клуб клиента нельзя.

Миграция `2026_11_13_030000_create_mobile_app_settings_table.php` создаёт таблицу и начальную запись: два контакта из примера выше, версия `1.0.0`, выключенные техработы и `#` для незаполненных ссылок. При редактировании нужно сохранять хотя бы один контакт, формат версии `X.Y.Z` и полный состав блоков. Параметры Reverb в этой таблице не хранятся: используется существующий ключ `REVERB_APP_KEY` и публичный адрес из `APP_URL`, отдельного мобильного ключа нет.

HTTP-ответ `/config` содержит `Cache-Control: no-store, private`, чтобы промежуточный кеш не удерживал старые настройки. Сохранённой копией управляет само приложение. Общий API-лимит запросов действует и здесь (`429`). Адрес API и формат телефона `+7` + 10 цифр остаются в приложении.

### Редактирование настроек в админке

Конфиг один на приложение: ID не передаётся ни в URL, ни в теле запроса, в ответе его тоже нет. Технический первичный ключ записи остаётся внутри БД.

- `GET /api/v1/mobile/config` — получить настройки для формы.
- `PATCH /api/v1/mobile/config` — частично изменить `contacts`, `app`, `maintenance`, `links`.

Обе ручки требуют Bearer-токен сотрудника и роль администратора или руководителя. Настройки общие для приложения, независимо от выбранного сотрудником клуба. Другие роли получают `403`, отсутствие авторизации и мобильный токен клиента — `401`. Ответ обеих ручек совпадает с публичным `/config`: `{ "data": {...} }`, включая `realtime` только для чтения. Ошибки ввода — стандартный формат админки `422` с полями в `errors`.

Пример частичного изменения:

```json
{
  "contacts": [
    { "title": "Позвонить", "url": "tel:+77758761111" },
    { "title": "Написать в WhatsApp", "url": "https://wa.me/77758761111" }
  ],
  "app": { "min_version": "1.1.0" },
  "maintenance": { "enabled": true, "message": "Техработы до 14:00" }
}
```

Непереданные поля сохраняются, включая вложенные: отправка только `app.store_url.ios` не меняет Android-ссылку или минимальную версию. Переданный `contacts` целиком заменяет список с сохранением порядка; пустой список запрещён. У контакта обязательны `title` до 255 символов и готовая ссылка `url` до 2048 символов со схемой (`tel:`, `https:`, другие схемы также допускаются). Версия — `X.Y.Z` до 32 символов. Ссылки магазинов и политики — HTTP/HTTPS или `#`, до 2048 символов.

При включении техработ нужно передать непустой `maintenance.message` до 2000 символов. Пока техработы включены, сообщение нельзя очистить; сначала или одновременно выключить `enabled`. Для выключения достаточно `{"maintenance":{"enabled":false}}`; публичный ответ вернёт `message: null`. Передавать `realtime` для изменения запрещено: ключ и адрес берутся из инфраструктурной конфигурации, не из БД. Сохранённые изменения видны публичной ручке при следующем запросе. Экран редактирования в админке подключается отдельно.

## 1. Вход по номеру телефона

### Текущий каркас

Реализованы `POST /auth/code`, `POST /auth/verify`, `POST /auth/logout`, `GET /me`, `GET /me/membership`, `GET /me/membership/history`, `GET /me/trinket`, `GET /me/pass`, `GET /me/visits` и `GET /trainers`. Провайдеры отправки пока не подключены: запрос кода не отправляет сообщений, проверка использует `__hardcoded('111111')`. Перед проверкой необходимо запросить код; запрос действует 5 минут и после успешной проверки больше не принимается. Повторный запрос до истечения этих 5 минут не обнуляет счётчик неверных попыток. На следующем этапе заглушка будет заменена реальной доставкой через Telegram Gateway и WhatsApp.

После проверки выдаётся настоящий бессрочный токен клиента через Laravel Sanctum. Мобильные маршруты используют `auth:mobile` с provider `clients`; сотрудники используют отдельный `auth:api` с provider `users`. Токены не принимаются чужим guard. Для хранения токенов нужна таблица `personal_access_tokens` из миграции Sanctum, доступной через `php artisan migrate`. Поддержка ключей устройств, бюджет платных отправок и остальные мобильные ручки пока остаются планом.

**`POST /auth/code`** — отправить код существующему клиенту клуба. Эта же ручка используется для повторной отправки.

Запрос: `{ "phone": "+77758761111" }`.

Ответ `200`: `{ "code_length": 6, "retry_after_seconds": 59 }`.

Если клиент с таким телефоном не найден — `404 PHONE_NOT_FOUND`. Приложение предложит обратиться в клуб. Если клиент есть, но активного абонемента нет, вход всё равно разрешён. При слишком частой отправке — `429 RATE_LIMITED` с оставшимся временем ожидания. Срок действия кода и лимит попыток определяет сервер.

Если нормализованному номеру соответствуют несколько неудалённых клиентов — `409 PHONE_AMBIGUOUS` с сообщением «Обратитесь к администратору для уточнения номера». Проверка выполняется до обращения к провайдеру: код не отправляется, платный запрос не создаётся. Автоматически выбирать первую, последнюю или имеющую активный абонемент карточку нельзя. После исправления контактов, когда номер однозначно соответствует одному клиенту, вход становится доступен без отдельного снятия блокировки.

**`POST /auth/verify`** — проверить код и выдать токен.

Запрос: `{ "phone": "+77758761111", "code": "123456" }`.

Ответ `200`: `{ "token": "..." }`. Неверный код — `422 INVALID_CODE`, истёкший — `422 CODE_EXPIRED`.

В текущем каркасе принимаются телефон в формате `+77XXXXXXXXX` и код из шести цифр как строка. Ошибки входных данных — `422 VALIDATION_ERROR`. После пяти неверных попыток проверка блокируется до истечения запроса кода: `429 RATE_LIMITED` с `error.retry_after_seconds`. Запросы кода ограничены одной отправкой в 60 секунд, тремя в час и пятью за 24 часа на номер; также действует общий API-лимит 60 запросов в минуту на IP.

При проверке кода однозначность номера проверяется повторно. Если с момента отправки кода появился другой неудалённый клиент с тем же нормализованным номером — `409 PHONE_AMBIGUOUS`, токен не выдаётся. Проверка кода привязана к исходному клиенту: изменение владельца номера между отправкой и проверкой не должно давать доступ к другой карточке.

**`POST /auth/logout`** — отозвать текущий мобильный токен. Требует `Authorization: Bearer <token>`. Ответ `204`, без тела. Другие токены клиента продолжают действовать. Недействительный или отсутствующий токен — `401 UNAUTHORIZED`.

В интерфейсе телефон вводится как десять цифр после `+7`; перед запросом приложение приведёт его к полному формату. Пока длина кода и таймер заданы константами — при интеграции возьмём их из ответа.

### План: ограничения на отправку кодов

- Коды отправляются только существующим клиентам клуба. Сначала используется официальный Telegram Gateway; при подтверждённой недоступности получателя — WhatsApp через AutoCall.kz. Ошибки настройки, нехватка баланса и сетевой таймаут не считаются подтверждением недоступности получателя.
- На один номер: не чаще одной отправки в 60 секунд, максимум 3 отправки в час и 5 в сутки. Лимиты общие для Telegram и WhatsApp; смена канала, IP или `device_id` их не обнуляет. Более строгие ограничения провайдера также учитываются.
- Дополнительно ограничиваются запросы по IP и устройству. `device_id` используется как дополнительный признак, а не как единственное средство защиты.
- Максимум 5 неверных попыток проверки одного кода, после чего код больше не принимается. Смена канала не должна обнулять счётчик попыток текущего кода.
- Повторные и одновременные запросы не должны создавать дубли платных отправок. Проверка лимитов и резервирование отправки выполняются атомарно на сервере.
- Начальный общий бюджет — 1 000 ₸ в сутки на оба канала. Перед платным запросом сервер атомарно резервирует стоимость; при неопределённом результате запроса резерв сохраняется до выяснения статуса. При исчерпании бюджета новые отправки останавливаются, действующие сессии продолжают работать. Сумма уточняется перед запуском под число клиентов и тарифы провайдеров.
- Превышение лимита номера возвращает `429 RATE_LIMITED` с `error.retry_after_seconds`. Для общего бюджета также используется `429 RATE_LIMITED`; причина записывается в серверный журнал. Отказ происходит до обращения к платному API.
- Отсутствие введённого кода само по себе не запускает отправку в WhatsApp. После паузы приложение может предложить пользователю запросить код в WhatsApp; эта отправка учитывается в тех же лимитах и бюджете.

### План: повторный вход по ключу устройства

- При первом входе приложение создаёт криптографическую пару ключей. После успешной проверки кода сервер привязывает публичный ключ к клиенту и устройству с проверкой владения приватным ключом. Приватный ключ хранится в защищённом хранилище устройства и не передаётся серверу.
- Токен не имеет срока истечения: приложение использует существующую сессию без отправки кодов до выхода или отзыва токена. При повторном входе после выхода зарегистрированное устройство подписывает одноразовый запрос сервера приватным ключом; после проверки подписи сервер выдаёт новый токен без кода из мессенджера.
- Запрос для подписи имеет короткий срок действия, связан с конкретной регистрацией ключа и может быть использован только один раз. Одного `device_id` или публичного ключа для входа недостаточно.
- Привязка нового ключа или замена существующего требует повторного подтверждения телефона кодом. При потере либо отзыве ключа пользователь проходит вход по коду заново.
- Явный выход отзывает только текущий токен на сервере; приложение удаляет локальный токен и данные сессии. Приватный ключ на устройстве и регистрация публичного ключа на сервере сохраняются без срока истечения, в том числе по неактивности, чтобы следующий вход с этого устройства проходил без кода.
- «Забыть устройство» — отдельное действие: отзывает регистрацию ключа и связанные с ней токены на сервере, удаляет локальный ключ и сессию. После этого для входа требуется код.
- Ручки регистрации ключа, получения запроса для подписи, входа по подписи и выхода нужно добавить при реализации этого этапа; их точные запросы и ответы пока не входят в описанный выше контракт `/auth/code` и `/auth/verify`.

## 2. Главный экран «Моя карта»

**`GET /me`** — данные клиента для приветствия и пропуска.

Ответ: `{ "data": { "first_name": "Алексей", "last_name": "Иванов" } }`.

Для мобильного API существующее поле клиента `name` разбирается по пробельным разделителям: первое слово — `last_name` (фамилия), второе — `first_name` (имя). Последующие слова относятся к отчеству и в этот ответ не включаются. Порядок в исходных данных фиксирован: фамилия, имя, отчество. Изменение структуры таблицы клиентов и форм админки не требуется.

**`GET /me/membership`** — абонементы для главного экрана.

```json
{
  "data": {
    "memberships": [
      {
        "id": "123",
        "title": "Тренажёрный зал",
        "status": "active",
        "active": true,
        "expires_soon": false,
        "limited": true,
        "visits_left": 12,
        "visits_total": 16,
        "purchased_at": "2026-10-23T10:00:00+05:00",
        "activated_at": "2026-10-23T17:00:00+05:00",
        "valid_until": "2026-11-23T23:59:59+05:00"
      }
    ],
    "last_membership": null,
    "message": "Поможем выбрать подходящий тариф. Напишите администратору или оформите абонемент на ресепшене клуба."
  }
}
```

- `memberships` содержит все текущие программы и безлимиты, включая ожидающие активации и замороженные. Порядок: `active`, затем `pending_activation`, затем `frozen`; внутри статуса — по убыванию ID покупки. Солярий не включается.
- `last_membership` — объект в том же формате, но со статусом `expired` или `exhausted`, если текущих абонементов нет. Выбирается последняя купленная завершённая карта по ID покупки. Если текущие есть или покупок не было, поле равно `null`. В основной список завершённые не подмешиваются.
- `status`: `active` — действует; `pending_activation` — ожидает активации; `frozen` — заморожен; `expired` — срок истёк; `exhausted` — посещения закончились. Если остаток ограниченного абонемента нулевой или отрицательный, статус `exhausted`, в том числе при заморозке или истёкшем сроке. Для остальных действующая заморозка имеет приоритет перед истечением исходной даты.
- `active` равен `true` только при `status: active`. Правила активации, заморозки, списания посещений и выдачи пропуска не изменяются.
- `expires_soon` — boolean, рассчитывается сервером и возвращается на главной и в истории. Равен `true` только для `active`, если осталось не более двух посещений у ограниченного абонемента либо дата окончания — сегодня или в ближайшие семь календарных дней включительно. Для безлимита учитывается только дата. Для остальных статусов всегда `false`.
- `limited: false` — безлимит; `visits_left` и `visits_total` в этом случае `null`. Остаток учитывает посещения и подтверждённые штрафные списания.
- `purchased_at` — дата покупки; `activated_at` — дата активации или `null`, если не записана. `valid_until` — конец последнего дня действия с часовым поясом, до активации `null`. Все даты — ISO 8601.
- Купленные абонементы остаются доступны, даже если соответствующий тариф удалён из каталога.

Правила мобильного экрана:

- Действующие абонементы показываются полными карточками, ожидающие активации и замороженные — компактными строками со статусом.
- Если действующих нет, но `memberships` не пуст, показываются имеющиеся покупки, без пустого состояния. Для ожидающих используется подпись «Ожидает активации»; для замороженных — «Заморожен» без выдуманной даты разморозки. Доступна кнопка связи с администратором.
- Если `memberships` пуст, но `last_membership` не `null`, показывается одна завершённая карта с причиной завершения и кнопкой «Продлить через администратора», ведущей в чат.
- Только если список пуст и `last_membership: null`, показывается «У вас пока нет абонемента», `message` и кнопка «Подобрать абонемент». Поле `message` остаётся строкой во всех ответах, но в других состояниях не отображается.
- Сворачиваемые блоки и разделители на главной не нужны. Ссылка «Все абонементы» открывает отдельный экран истории.
- При `expires_soon: true` в карточке показывается «Скоро закончится — написать администратору». Нажатие открывает чат. Пропуск остаётся доступен любому авторизованному клиенту с выданной картой независимо от абонемента.

**`GET /me/membership/history?limit=20&cursor=0`** — история всех покупок программ и безлимитов владельца токена, включая текущие и завершённые.

```json
{
  "data": {
    "items": [
      {
        "id": "123",
        "title": "Тренажёрный зал",
        "status": "expired",
        "active": false,
        "expires_soon": false,
        "limited": true,
        "visits_left": 2,
        "visits_total": 16,
        "purchased_at": "2026-09-01T10:00:00+05:00",
        "activated_at": "2026-09-02T17:00:00+05:00",
        "valid_until": "2026-10-02T23:59:59+05:00"
      }
    ],
    "next_cursor": 456
  }
}
```

По умолчанию `limit=20`, допустимо от 1 до 50. `cursor=0` означает первую страницу. Порядок — по убыванию ID покупки. Следующий числовой курсор — ID покупки (`Sale`), а не ID абонемента (`ServiceSale`) из поля `id`; приложение передаёт `next_cursor` без изменений. Новые покупки не сдвигают следующие страницы. На последней странице курсор `null`. Пустая история: `{ "data": { "items": [], "next_cursor": null } }`. Неверные параметры — `422 VALIDATION_ERROR`; отсутствие мобильной авторизации — `401 UNAUTHORIZED`.

**`GET /me/trinket`** — выданный клиенту ключ от шкафчика.

Ответ: `{ "data": { "number": "17" } }` или `{ "data": null }`, если ключ не выдан либо уже возвращён. Ключ определяется по незавершённому посещению авторизованного клиента; завершённые посещения не учитываются. Возвращается номер шкафчика строкой, а не код брелока. Приложение только показывает ключ, выдача и возврат происходят на стороне клуба.

**`GET /me/pass`** — код для штрихкода на экране пропуска.

Ответ: `{ "data": { "code": "6287938", "format": "CODE128" } }`.

Текущая реализация возвращает `CODE128` и исходный код привязанной карты строкой, сохраняя ведущие нули. Данные берутся из связи клиента с картой, а не из кешированного номера. Пропуск доступен любому авторизованному клиенту с выданной картой независимо от наличия активного абонемента. Если карта не выдана — `403 PASS_UNAVAILABLE`. Код статический, без срока обновления.

## 3. Посещения

**`GET /me/visits?limit=20&cursor=0`** — история посещений, от новых к старым.

Ответ: `{ "data": { "items": [{ "id": "123", "at": "2026-10-22T17:00:00+05:00" }], "next_cursor": 123 } }`.

На главном экране нужны последние три посещения: та же ручка с `limit=3`. По умолчанию `limit=20`, допустимо от 1 до 50; `cursor=0` означает первую страницу. Посещения упорядочены по убыванию ID. Следующий числовой курсор — ID последнего посещения возвращённой страницы, а не смещение; клиент передаёт его без изменений. Новые посещения между запросами не сдвигают следующие страницы. На последней странице `next_cursor: null`. Без посещений: `{ "data": { "items": [], "next_cursor": null } }`. Включаются открытые и завершённые посещения; `at` — время начала посещения в ISO 8601 с часовым поясом. Возвращаются только посещения владельца токена. Некорректные параметры — `422 VALIDATION_ERROR`. Группировку по месяцам делает приложение.

## 4. Тренеры и клуб

**`GET /trainers`** — отдельный список тренеров клуба, требующий мобильный токен. Тренеры хранятся в таблице `trainers`, независимо от сотрудников и их ролей. Возвращаются только записи с `is_active: true`, по возрастанию `sort_order`, затем ID.

Ответ: `{ "data": [{ "id": "1", "first_name": "Александр", "last_name": "Волков", "specialization": "Силовые тренировки", "photo_url": "https://.../trainer-mobile.jpg" }] }`. Если тренеров нет — `{ "data": [] }`.

`photo_url` может быть `null` — тогда показывается иконка. Имена и специализация обязательны. Фото хранится через Media Library; API возвращает готовый URL синхронно подготовленного изображения 600×600.

### Управление тренерами в админке

Административные ручки находятся под `/api/v1` и требуют Sanctum-токен сотрудника с ролью администратора или руководителя. Проверка прав выполняется сервером для всех операций.

- `GET /api/v1/trainers` — весь список, включая скрытых, в порядке `sort_order`, затем ID.
- `POST /api/v1/trainers` — создать тренера; ответ `201`.
- `GET /api/v1/trainers/{trainer}` — получить тренера; ответ `200`.
- `PATCH /api/v1/trainers/{trainer}` — частично изменить поля; ответ `200`. `PUT` также поддерживается с теми же правилами.
- `DELETE /api/v1/trainers/{trainer}` — удалить тренера и его фотографии; ответ `204` без тела.

Поля создания: `first_name`, `last_name`, `specialization` — обязательные непустые строки до 255 символов. Необязательные: `sort_order` — целое число от 0 до 4294967295 (по умолчанию 0), `is_active` — boolean (по умолчанию true), `photo` — JPEG или PNG до 5 МБ. При обновлении передаются только изменяемые поля. Для скрытия тренера используется `is_active: false`.

Загрузка фото выполняется через `multipart/form-data`. Для обновления фотографии используется `POST /api/v1/trainers/{trainer}` с полем `_method=PATCH`, чтобы PHP разобрал загруженный файл. Новая фотография заменяет старую. Отсутствие поля `photo` сохраняет прежнее фото; `photo: null` в JSON удаляет его. Ошибка обработки загруженного файла откатывает изменения и удаляет новые файлы, сохраняя прежнюю фотографию; исключение не скрывается.

Административный ответ имеет обёртку `data` и поля мобильной карточки плюс `sort_order` и `is_active`. Список — `{ "data": [...] }`, отдельная запись — `{ "data": {...} }`. Недостаточно прав — `403`, нет авторизации — `401`, запись не найдена — `404`; ошибки ввода используют существующий формат админки `422` с `errors` по полям.

Перед подключением ручек необходимо выполнить миграцию `2026_11_12_000000_create_trainers_table.php`. Раздел интерфейса админки подключается к этим ручкам отдельно.

**`GET /club`** — информация о клубе авторизованного клиента. Требуется мобильный токен. Клуб определяется только по `clients.club_id`; приложение не передаёт ID клуба и не выбирает филиал. При смене привязки клиента ручка возвращает новый клуб без изменения приложения.

```json
{
  "data": {
    "id": "2",
    "name": "Гладиаторы",
    "cover_url": "https://.../club.jpg",
    "address": "г. Павлодар, ул. Примерная, 10",
    "map_url": "https://...",
    "schedule": [
      { "days": "Пн–Пт", "hours": "08:00–22:00" },
      { "days": "Сб–Вс", "hours": "10:00–20:00" }
    ],
    "phone": "+77758761111",
    "whatsapp": "77758761111",
    "instagram": "gladiators8"
  }
}
```

Данные экрана хранятся в отдельной таблице `club_profiles`: одна запись на клуб, уникальный `club_id`. Существующая таблица `clubs` сохраняет прежние поля. Обложка принадлежит профилю и хранится через медиатеку. Профиль создаётся при первом сохранении через API админки; миграция не заполняет контакты вымышленными значениями. Пока профиль не заполнен, контактные поля, адрес, карта и обложка равны `null`, расписание — `[]`. Подписи расписания приходят готовыми. WhatsApp — только цифры, Instagram — имя без `@`. Без токена — `401`; если привязанный клуб не существует — `404`.

### Управление информацией о клубе в админке

- `GET /api/v1/clubs/{club}` — получить информацию.
- `PATCH /api/v1/clubs/{club}` — частично обновить `address`, `map_url`, `schedule`, `phone`, `whatsapp`, `instagram`, `cover`. Название и привязки клиентов этим запросом не меняются.
- `GET /api/v1/clubs` — существующий список клубов, контракт не меняется.

Просмотр подробностей и изменение доступны администратору и руководителю только для клубов из их связи `club_user`. Иная роль или недоступный клуб — `403`; мобильный токен не даёт доступа к API админки. Ответ подробностей и изменения совпадает с мобильным и содержит обёртку `data`.

`map_url` — HTTP/HTTPS-ссылка до 2048 символов. `phone` — строка до 32 символов, допускает `+`, пробелы, скобки и дефисы; `whatsapp` — строка из 7–15 цифр; `instagram` — до 30 латинских букв, цифр, точек и подчёркиваний. `schedule` — до 14 строк с обязательными непустыми строками `days` и `hours` до 100 символов. Поля профиля можно очистить значением `null`, расписание также допускает `[]`.

`cover` — JPG/JPEG/PNG до 5 МБ. Для загрузки используется `POST /api/v1/clubs/{club}` с `multipart/form-data` и `_method=PATCH`; для удаления — JSON `{"cover": null}`. Без поля `cover` прежняя обложка сохраняется, новая заменяет старую. Ошибки ввода возвращаются в существующем формате админки `422` с `errors` по полям.

Перед подключением ручки выполнить миграцию `2026_11_13_020000_create_club_profiles_table.php`. Интерфейс редактирования в админке подключается отдельно.

## 5. Чат с администратором

Один диалог на клиента, только текстовые сообщения. Доступен и без активного абонемента. Администратор читает диалоги и отвечает в существующей админке; для этого нужно добавить список диалогов, счётчики непрочитанных и просмотр и отправку сообщений.

Доступ к списку диалогов, чтению переписки и отправке ответов в админке имеют только сотрудники с ролью администратора или руководителя. Ограничение проверяется на сервере для всех административных ручек чата, а также учитывается при отображении раздела в интерфейсе.

**`GET /me/chat/messages`** — история, от старых сообщений к новым.

Ответ — массив объектов: `{ "id": "message-1", "direction": "incoming", "text": "Добрый день!", "sent_at": "2026-10-22T17:00:00+05:00" }`.

`direction`: `incoming` — от администратора, `outgoing` — от клиента. Без сообщений возвращается `[]`. Сейчас мобильный код загружает всю историю; пагинацию и способ получения новых сообщений (опрос или realtime) нужно согласовать до подключения реального чата.

**`POST /me/chat/messages`** — отправить сообщение.

Запрос: `{ "text": "Как продлить абонемент?", "client_message_id": "уникальный-id" }`.

Ответ `201` — сохранённый объект сообщения, как в истории, с `direction: "outgoing"`. Повторный запрос с тем же `client_message_id` должен вернуть то же сообщение без дубля. В приложение нужно добавить передачу этого ID при интеграции. Статусы «Отправка» и «Не отправлено» ведёт мобильный клиент.

**`GET /me/chat/unread`** → `{ "count": 2 }` — число непрочитанных сообщений от администратора.

**`POST /me/chat/read`** с `{ "last_read_message_id": "message-1" }` → `204` — отметить прочитанными сообщения до указанного включительно. Новые сообщения, пришедшие позже, остаются непрочитанными. Эти две ручки ещё не подключены: сейчас счётчик хранится локально.

## Ошибки и сессия

Единый формат ошибки:

```json
{
  "error": {
    "code": "INVALID_CODE",
    "message": "Неверный код подтверждения"
  }
}
```

Для `429` дополнительно: `error.retry_after_seconds`. Приложение различает ошибки по `code`, не по тексту. `401 UNAUTHORIZED` означает, что токен недействителен: нужно удалить локальный токен и перейти к входу; ключ устройства сохраняется для повторного входа без кода. `5xx` и отсутствие сети позволяют повторить запрос, не подменяя данные пустыми.

Токен хранится в защищённом хранилище устройства, не имеет срока истечения и действует до отзыва. Refresh-token не предусмотрен. При реализации выхода необходимо добавить серверный отзыв текущего токена и удаление локальных данных сессии с сохранением ключа устройства. Повторный вход по зарегистрированному ключу выдаёт новый токен без отправки кода; при потере либо отзыве ключа открывается экран подтверждения телефона. Выход не запускает повторный вход автоматически — он происходит, когда пользователь снова решает войти.

## Что не входит в текущий объём

Регистрация новых клиентов, покупка и оплата абонемента, запись на тренировку, вложения в чате и push-уведомления пока не реализованы. Кнопка «Подобрать абонемент» открывает чат, а не создаёт заказ.
