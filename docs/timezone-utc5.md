# UTC+5 для этого проекта

## Проверено на сервере

PHP 7.4 использует системную базу часовых поясов (`0.system`), в которой `Asia/Almaty` всё ещё UTC+6. MySQL-соединение использует `SYSTEM`, также UTC+6. Мобильное приложение преобразует ISO-даты в актуальное время телефона; админка выводит подготовленный сервером текст.

`sessions.created_at`, `finished_at`, все остальные `created_at`, `updated_at`, `deleted_at` и временные поля токенов имеют тип `TIMESTAMP`. В отдельном соединении проверено: смена `SESSION time_zone` с `+06:00` на `+05:00` меняет чтение посещения с `21:43:21` на `20:43:21`, сохраняя само событие. Обновлять эти записи SQL-запросами нельзя: получится двойной сдвиг.

Три бизнес-поля хранят момент события как `DATETIME`: `service_sale.activated_at`, `stop_cards.unstopped_at`, `transactions.cancelled_at`. Их нужно однократно перевести из прежнего UTC+6 в UTC+5. `service_sale.active_until` — календарный срок действия, хотя его тип также `DATETIME`; он остаётся без изменений. Все `DATE`, включая дни рождения и сроки заморозки/восстановления, остаются без изменений. Старый диагностический журнал Telescope не входит в бизнес-историю и остаётся в исходном виде.

## План реализации

- [x] Воспроизвести ошибку тестами на PHP 7.4 и отдельной MariaDB с искусственными данными.
- [x] В `config/app.php` задать `Etc/GMT-5` (фиксированный UTC+5); в `config/database.php` задать `mysql.timezone = '+05:00'`. Laravel устанавливает пояс только своего SQL-соединения.
- [x] Добавить миграцию `2026_11_13_000000_convert_datetime_instants_to_utc_plus_five.php`: в транзакции вычесть час только из трёх бизнес-полей `DATETIME`. `down()` прибавляет час к тем же полям. NULL и остальные поля не меняются.
- [x] Проверить сохранение момента старого посещения, запись нового, границу суток, неизменность календарных сроков и обратное преобразование миграции; запустить мобильные тесты.
- [x] Перед применением сохранить резервную копию БД и двух конфигурационных файлов вне публичной директории. На время переключения остановить запись через maintenance mode проекта, убедиться, что старые запросы завершились.
- [x] Заменить только две настройки и добавить миграцию. Запустить `php artisan migrate --force --path=database/migrations/2026_11_13_000000_convert_datetime_instants_to_utc_plus_five.php`, используя PHP 7.4 сайта. Если конфигурация была закэширована, пересобрать её. Перезапустить только воркеры этого проекта, если они запущены. Возобновить работу проекта.
- [x] Сверить PHP UTC+5, `@@session.time_zone = '+05:00'`, старое посещение и календарные сроки. Общие параметры ОС, MySQL и PHP-FPM, фронт и мобильное приложение не менять.

## Откат

В maintenance mode сначала выполнить `php artisan migrate:rollback --force --path=database/migrations/2026_11_13_000000_convert_datetime_instants_to_utc_plus_five.php`. Затем восстановить обе прежние конфигурации, вернуть прежний режим кэширования конфигурации и перезапустить только воркеры проекта, если они были запущены. Проверить UTC+6 и прежнее чтение посещения, затем выполнить `php artisan up`.

Миграцию нельзя запускать вручную повторно: однократность обеспечивает таблица Laravel `migrations`. Восстановление полной копии БД применяется только при необходимости, поскольку оно удаляет последующие записи.

## Результат применения 12 ноября 2026

Применено на `api.gladiatory.ariesdev.kz`, PHP 7.4. Резервная копия БД (gzip проверен) и прежние конфигурации: `storage/app/backups/timezone-utc5-20261112-162754/` на сервере. В этой же закрытой директории сохранены контрольные данные до переключения.

Проверены суммы Unix-времени всех посещений и трёх преобразованных полей, а также `created_at`/`updated_at` затронутых таблиц: реальные моменты событий сохранены. Контрольная сумма календарных сроков абонементов не изменилась. Глобальный часовой пояс БД не менялся; воркеров этого сайта не было, процессы других сайтов не перезапускались. Кэш конфигурации на сайте отсутствовал и не создавался.

Реальный HTTP-запрос `/api/mobile/v1/me/visits?limit=1` вернул `200`, посещение `142950` — `2026-11-12T20:43:21+05:00`; серверное отображение для админки — `12.11.2026 20:43:21`. Временный проверочный токен удалён. Сайт выведен из maintenance mode.

Проверки: 107 тестов мобильного API, тренеров и конфигурации (492 проверки); ещё 3 интеграционных теста в отдельной MariaDB (28 проверок). Для интеграционных тестов используется только выделенная БД `fitness_timezone_test` с искусственными данными; они запускаются явно через `php vendor/bin/phpunit tests/Integration/TimezoneTest.php`. Созданный для проверки контейнер удалён.
