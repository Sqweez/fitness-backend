# Перенос приложения Gladiators в Docker

## Обследование 12 ноября 2026

Обследование выполнено только на чтение. Контейнеры на сервере не запускались, настройки Plesk, nginx, PHP, cron и БД не изменялись.

- Сервер: CentOS 7.9, ядро `3.10.0-1160.102.1.el7.x86_64`, Plesk Obsidian 18.0.57.3.
- Docker 25.0.3 и Compose v2.21.0 уже установлены, daemon работает. Контейнеров и образов нет. Storage driver — overlay2, cgroup v1. Firewalld включён, SELinux отключён.
- Около 5,7 ГБ RAM, доступно около 2,4 ГБ; занято около 0,85 ГБ swap. Во время короткой проверки `vmstat` активного обмена со swap не было. На диске около 13 ГБ свободно. Это позволяет рассматривать небольшой стек приложения, но его расход памяти нужно проверить при подготовке.
- Домен `api.gladiatory.ariesdev.kz`: Plesk nginx принимает HTTPS и проксирует в Apache на порт 7081. Сертификат обслуживает Plesk.
- Веб-обработчик в сгенерированном Apache-конфиге — `plesk-php80-fastcgi`. Установлен PHP 8.0.30. Cron этого проекта тоже использует `/opt/plesk/php/8.0/bin/php`. Более ранние проверки через CLI 7.4 не означают, что веб-запросы обслуживаются PHP 7.4.
- Каталог: `/var/www/vhosts/ariesdev.kz/api.gladiatory.ariesdev.kz`; владелец `ariesdev_kz`, UID 10000, GID 1003.
- `storage` занимает около 1,5 ГБ, в таблице `media` — 5267 записей. `public/storage` — абсолютная ссылка на `storage/app/public` текущего проекта. При другом пути внутри контейнера ссылку нужно создать заново.
- MariaDB 10.2.44 работает на хосте, БД проекта около 78 МБ. Laravel подключается к `127.0.0.1:3306`, аккаунт разрешён как `admin_topstar@%`. Из контейнера адрес `127.0.0.1` укажет на сам контейнер; подключение к БД нужно настроить отдельно и проверить с учётом firewalld.
- Дополнительно сверены настройки проектов и список схем: `admin_topstar` (34 таблицы, 77,7 МБ) используется Gladiators. Ironadmin и iron-addicts подключаются к `p-2321325_ironadmin`, Tooman — к `admin_tooman_crm`, Twerk — к `admin_twerk`; все эти подключения идут в тот же сервер MariaDB на порту 3306. В нём также есть служебная база Plesk `psa`. Перенести только `admin_topstar` в контейнер можно независимо от остальных баз. Наличие других баз запрещает выключать общий сервер MariaDB, но не является причиной откладывать перенос самой `admin_topstar`.
- Пояс Laravel — `Etc/GMT-5`, пояс SQL-соединения — `+05:00`. Уже применённую миграцию часового пояса повторно не запускать вручную.
- Кэш и сессии — файловые, очередь — `sync`, broadcasting — `log`. Проект сейчас не использует Redis для очереди или кэша и не имеет работающего WebSocket-сервера.
- В cron пользователя `ariesdev_kz` есть ежеминутный `schedule:run` именно этого проекта. Отдельных Supervisor-воркеров Gladiators нет; имеющиеся воркеры относятся к другим проектам.
- Docker-расширение Plesk не установлено. Для переключения нужен конфиг только этого домена, без установки расширения и изменения общих шаблонов.

## Предлагаемый объём первой ночи

Согласованный объём: перенести приложение, его базу `admin_topstar` и scheduler. MariaDB других проектов оставить на хосте. Общие PHP, nginx, Apache, Redis, Docker daemon, ОС и другие сайты не обновлять. Не совмещать контейнеризацию со сменой версии PHP, настройкой WebSocket и CI/CD.

Схема: Plesk nginx с прежним HTTPS → локальный порт контейнерного nginx → контейнер PHP 8.0 FPM → отдельная MariaDB 10.2.44 в Docker. Контейнер scheduler использует тот же образ приложения. Новый публичный порт для приложения не требуется: контейнерный nginx публикуется только на loopback хоста.

Начальную версию PHP сверить с реальным веб-обработчиком. Для будущего обновления PHP достаточно отдельно подготовить новый образ и пройти проверки; контейнеризация сама по себе не решает совместимость старых зависимостей с новым PHP.

Очередь `sync` при первом переключении сохранить. Redis, queue worker и WebSocket добавить отдельным изменением, когда будут подготовлены соответствующие функции приложения.

## Что подготовить в репозитории

1. Отдельный production Dockerfile: PHP 8.0, необходимые расширения из `composer.lock`, зависимости через `composer install --no-dev` без изменения lock-файла, код конкретного коммита внутри образа. Секреты, резервные копии и пользовательские файлы не должны попадать в build context или образ.
2. Отдельный production Compose: nginx, PHP, MariaDB и scheduler; уникальное имя проекта, лимиты ресурсов, restart policy. Scheduler первоначально выключен. Не запускать текущий development Compose на боевом сервере: он публикует MySQL на занятый 3306, создаёт другую БД и использует PHP 7.4 вместо настроенного веб-PHP 8.0.
3. Сохранить существующие `APP_KEY` и прочие секреты; не генерировать их заново. Прежние пользовательские данные и токены переносятся полным дампом базы вместе с таблицей `migrations`. `DB_HOST`/`DB_SOCKET` адаптировать для контейнера; пояс соединения оставить `+05:00`.
4. Подключить постоянное хранилище с существующими медиа, файловым кэшем и сессиями. PHP запускается с подходящими UID/GID; `bootstrap/cache` должен быть доступен на запись в окружении контейнера, кэш конфигурации от хоста не переносить.
5. Проверить HTTPS и forwarded headers, чтобы URL фотографий не стали HTTP, авторизация сотрудников и клиентов сохранилась, а ограничения по IP не начали считать всех клиентов одним адресом прокси.
6. Подготовить настройки reverse proxy и их откат для одного домена через поддерживаемые настройки Plesk. Нельзя просто дописать второй `location /` в текущий конфиг: он уже определён автоматически. Сгенерированные `nginx.conf`/`httpd.conf` напрямую не редактировать.

## Порядок проверки и переключения

1. Собрать amd64-образ и проверить его на текущем ядре сервера. Для сборки не занимать все ресурсы сервера с другими сайтами; при необходимости собирать отдельно и загружать готовый образ.
2. Запустить пробную копию на другом локальном порту, без трафика пользователей и без scheduler. Для проверок, меняющих данные, использовать восстановленную тестовую копию БД и отдельное файловое хранилище.
3. Проверить Composer platform requirements, мобильные и административные API, авторизацию, чтение/создание посещения, фотографии и их преобразования, сохранность файлов после пересоздания контейнера, UTC+5. `/` намеренно возвращает 404 и не подходит для healthcheck; для проверки загрузки Laravel можно использовать публичный маршрут документации.
4. Перед переключением сохранить свежую резервную копию БД, файлов, настроек домена и его cron. Сохранить старую рабочую установку для возврата.
5. В коротком окне обслуживания остановить запись, дождаться завершения запросов, подключить окончательное постоянное хранилище. Сделать финальный согласованный дамп после остановки записи и импортировать его в контейнерную MariaDB. Проверить суммы временных меток и календарные сроки. Выполнять только действительно необходимые миграции; сама контейнеризация изменения схемы БД не требует.
6. Переключить только домен API. Проверить `nginx -t` до reload; не перезапускать общий nginx без необходимости. Reload перечитывает общую конфигурацию, поэтому перед ним убедиться, что изменения ограничены этим доменом.
7. Отключить только строку `schedule:run` Gladiators в cron, затем включить контейнерный scheduler. Проверить, что одновременно работает один scheduler; cron и воркеры остальных проектов не менять.
8. Проверить реальный HTTPS API, вход сотрудника, вход клиента, посещение, медиа, URL с HTTPS, логи, RAM и ошибки; возобновить работу.

## Откат

Выключить контейнерный scheduler, вернуть прежние настройки домена и cron Gladiators. Если запись в новой БД ещё не открывали, можно вернуть прежнюю БД. Если в контейнерной БД уже появились записи, сначала остановить запись и перенести актуальные данные обратно; иначе новые посещения и продажи будут потеряны. Постоянное файловое хранилище должно быть общим для старой и новой установки либо синхронизировано перед возвратом. Старый код и зависимости на хосте сохраняются до завершения проверки переезда.

## Оценка и незакрытые проверки

Это перенос средней сложности: реалистично готовить и проверять в течение нескольких часов, а не обещать полный переезд за десять минут. Основные проверки до решения о переключении — запуск образа на старом ядре, доступ из контейнера к MariaDB, запись в хранилище, reverse proxy Plesk и совместимость зависимостей с выбранным PHP.

Docker уже установлен, поэтому обновление Docker/ОС в эту ночь не требуется. CentOS 7 отсутствует в текущем списке поддерживаемых систем официальной инструкции Docker; контейнеры не обновляют ядро хоста. Обновление ОС — отдельная задача.
